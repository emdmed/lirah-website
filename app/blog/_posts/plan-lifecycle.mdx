# I Started Using Plans Again, for Traceability

AI is letting engineers work on several tasks in parallel, and a very common issue in our everyday jobs is getting a question about a feature we did last week and having a complete mental gap about what we did and how it was implemented.

Fixing this is very difficult and we are all looking for a neat solution.

> I don't have it, but I am moving towards it.

## Plans, for traceability

I've started using plans again, not because they are better or worse than just asking the agent to do things directly, but **for traceability**.

I use plans for features, big bugfixes, or any very relevant code. I first draft them in one or several files (`architecture.md`, `feature.md`, `qa.md`) and then I unify them into a (frequently long) detailed implementation plan.

## Chunks in a clean context

So I created the plan feature in Lirah to support this, but with a catch: the final plan is broken down into committable steps, and when Lirah runs the plan each "chunk" is implemented in a clean context by default.

### Why?

- Less context degradation.
- The plan can be as long as I want without reaching a context window limit.

Also, each chunk is committed separately, so we have traceability and we can revert a given commit if need be.

## A lifecycle for each plan

So now each plan has a lifecycle: `planned`, `building`, `implemented`, `merged`.

<Figure name="lifecycle">The steps of that same plan, with what it left at each. **Filled squares left a record.** It started from a plan file, so it has no task, and its review left no notes.</Figure>

Tracking this over time not only helps me look back every Friday at what I got done that week. If I need to implement a later change, or need some context for an adjacent feature or bugfix, I have a history of what was done.

### For example

I got feature 1 done last week, and now feature 2 uses part of feature 1. I could just have the agent find and read all the code and implement it, no sweat.

But for me, the cleanest way to approach this is to have it read the feature 1 chunks, check the plan if necessary, and get a better result when implementing feature 2.

## How exactly do we keep the context clean between chunks?

At implementation time, the agent doing the work in chunk 1 might realize that something must be implemented a little differently than it was planned, so it writes a short handoff to the next chunk in the git commit message, as `Decision:` lines.

Before chunk 2 starts, Lirah reads the chunk 1 commit and puts those lines in the prompt, so the agent makes the necessary adjustments.

<Figure name="carry">Each prompt carries every decision written before it. **The prompt for chunk 5 carried 7 decisions from 4 commits**, to an agent that had seen none of them being made.</Figure>

## The work log

To complement this plan feature I also introduced the Lirah work log, which stores what you prompted, in which repo, on which branch, when, and which files changed (it works with Claude Code prompts only).

So you can ask an agent to look at your last 2 weeks of work log and it will tell you what you worked on, and can link it to any drafted or implemented plan.

<Figure name="drift">The plan against the work log. Three chunks changed exactly the files the plan listed. **Chunks 3 and 5 each changed one file the plan didn't list**, and chunk 5 left two listed ones alone.</Figure>
